# Server

Term: MQTT-SN Server (see the terminology section).

Sends: ADVERTISE, AUTH, CONNACK, DISCONNECT, GWINFO, PINGRESP, PROTECTION ENCAPSULATION, PUBACK, PUBCOMP, PUBLISH, PUBREC, PUBREL, PUBWOS, REGACK, SLEEPRESP, SUBACK, UNSUBACK, WAKEUP

Receives: AUTH, CONNECT, CONNECTION ENCAPSULATION, DISCONNECT, FORWARDER ENCAPSULATION, PINGREQ, PROTECTION ENCAPSULATION, PUBACK, PUBCOMP, PUBLISH, PUBREC, PUBREL, PUBWOS, REGISTER, SEARCHGW, SLEEPREQ, SUBSCRIBE, UNSUBSCRIBE

## Statements binding the Server (112)

- [MQTT-SN-3.1.2-2] The Server MUST validate that the reserved flags in the CONNECT packet are set to 0. (subject)
- [MQTT-SN-3.1.2.1-1] If a CONNECT packet is received with Clean Start is set to 1, the Client and Server MUST discard any existing Session and start a new Session. (subject)
- [MQTT-SN-3.1.2.1-2] If a CONNECT packet is received with Clean Start set to 0 and there is a Session associated with the Client Identifier, the Server MUST resume communications with the Client based on state from the existing Session. (subject)
- [MQTT-SN-3.1.2.1-3] If a CONNECT packet is received with Clean Start set to 0 and there is no Session associated with the Client Identifier, the Server MUST create a new Session. (subject)
- [MQTT-SN-3.1.2.7-1] If this flag is set to 0, the Server MUST NOT include a Server Keep Alive field in the CONNACK Packet response. (subject)
- [MQTT-SN-3.1.2.7-2] If this flag is set to 0, the Server MUST NOT include a Session Expiry field in the CONNACK Packet response. (subject)
- [MQTT-SN-3.1.2.7-3] If this flag is set to 0 for the current Virtual Connection, the Server MUST NOT include a Sleep Duration in the SLEEPRESP Packet. (subject)
- [MQTT-SN-3.1.3.3-1] If the Will Flag is set to 1 and Will Retain is set to 0, the Server MUST publish the Will Message as a non-retained message. (subject)
- [MQTT-SN-3.1.3.3-2] If the Will Flag is set to 1 and Will Retain is set to 1, the Server MUST publish the Will Message as a retained message. (subject)
- [MQTT-SN-3.1.5-2] If the Protocol Version is not 2 and the Server does not want to accept the CONNECT packet, the Server MAY send a CONNACK packet with Reason Code 0x84 (Unsupported Protocol Version). (subject)
- [MQTT-SN-3.1.7-2] The Server MUST NOT send packets exceeding Maximum Packet Size to the Client. If a Client receives a packet whose size exceeds this limit, this is a Protocol Error, the Client uses DISCONNECT with Reason Code 0x95 (Packet too large). (subject)
- [MQTT-SN-3.1.7-3] Where a Packet is too large to send, the Server MUST discard it without sending it and then behave as if it had completed sending that Application Message. (subject)
- [MQTT-SN-3.1.9-1] The Client and Server MUST store the Session State after the Virtual Connection is deleted if the Session Expiry Interval is greater than 0. (subject)
- [MQTT-SN-3.1.18-3] When the Client Identifier is present (greater than 0 bytes), the Server MUST allow values which are between 1 and 23 UTF-8 encoded bytes in length, and that contain only the characters \"0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ". (subject)
- [MQTT-SN-3.1.18-4] The Server MAY choose to allow more than 23 bytes. (subject)
- [MQTT-SN-3.1.19-1] The Server MUST validate that the CONNECT packet matches the format described in [sec](#connect---connection-request) and MUST NOT create a Virtual Connection for this CONNECT if it does not match. (subject)
- [MQTT-SN-3.1.19-2] The Server MAY check that the contents of the CONNECT packet meet any further restrictions and SHOULD perform authentication and authorization checks. If any of these checks fail, it MUST NOT create a Virtual Connection for this CONNECT. (subject)
- [MQTT-SN-3.1.19-4] The Server MUST perform the processing of Clean Start that is described in [sec](#clean-start-flag). (subject)
- [MQTT-SN-3.1.19-5] The Server MUST acknowledge the CONNECT packet with a CONNACK packet containing a 0x00 (Success) Reason Code. (subject)
- [MQTT-SN-3.1.19-7] The Server MUST interpret any Packet received from the Client (other than AUTH) that requires a Virtual Connection, after the CONNECT packet is received and before the CONNACK response is sent, as a Protocol Error. (subject)
- [MQTT-SN-3.2.2-1] Bits 7-4 of the CONNACK Flags are reserved and MUST be set to 0. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.2.1-1] If the Server accepts a CONNECT with Clean Start set to 1, the Server MUST set Session Present to 0 in the CONNACK Packet in addition to setting a 0x00 (Success) Reason Code in the CONNACK packet. (subject)
- [MQTT-SN-3.2.2.2-1] ​​If the Session Expiry Interval Flag is set to 0, a Session Expiry Interval MUST NOT be present in the Packet. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.2.2-2] If the Session Expiry Interval Flag is set to 1, a Session Expiry Interval MUST be present in the Packet. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.2.3-1] ​​If the Server Keep Alive Flag is set to 0, a Server Keep Alive field MUST NOT be present in the Packet. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.2.3-2] If the Server Keep Alive Flag is set to 1, a Server Keep Alive field MUST be present in the Packet. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.2.4-1] ​​If the Authentication Flag is set to 0, Authentication Method and Data MUST NOT be present in the Packet. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.2.4-2] If the Authentication Flag is set to 1, Authentication Method and Data MUST be present in the Packet. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.6-2] If the Server does not send the Server Keep Alive, the Server MUST use the Keep Alive value set by the Client on CONNECT. (subject)
- [MQTT-SN-3.2.11-1] The Assigned Client Identifier MUST be a UTF-8 Encoded String. (sender of CONNACK (packet format))
- [MQTT-SN-3.2.11-2] If the Client connects using a zero length Client Identifier, the Server MUST respond with a CONNACK containing an Assigned Client Identifier. (subject)
- [MQTT-SN-3.2.11-3] The Assigned Client Identifier MUST be a new Client Identifier not used by any other Session currently in the Server. (sender of CONNACK (packet format))
- [MQTT-SN-3.4.2-2] The receiver MUST validate that the reserved flags in the REGISTER packet are set to 0. If any of the reserved flags is not 0 it is a Malformed Packet. (receiver of REGISTER)
- [MQTT-SN-3.5.2-1] Bits 7-3 of the REGACK Flags are reserved and MUST be set to 0. (sender of REGACK (packet format))
- [MQTT-SN-3.5.2.2-1] If the Topic Alias Flag is set to 0, a Topic Alias MUST NOT be present in the Packet. (sender of REGACK (packet format))
- [MQTT-SN-3.5.2.2-2] If the Topic Alias Flag is set to 1, a Topic Alias MUST be present in the Packet. (sender of REGACK (packet format))
- [MQTT-SN-3.6.1.2-1] Bits 7-5 and 3-2 of the PUBWOS FLAGS are reserved and MUST be set to 0. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.1.2-2] The receiver MUST validate that the reserved flags in the PUBWOS packet are set to 0. If any of the reserved flags is not 0 it is a Malformed Packet. (receiver of PUBLISH)
- [MQTT-SN-3.6.1.4-1] If the Topic Type is Topic Name, the Topic Name field MUST be present in the PUBWOS packet. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.1.4-2] If the Topic Type is Predefined Topic Alias, the Topic Name field MUST NOT be present in the PUBWOS packet. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.2-1] PUBLISH packets received by a Client or Server MUST be associated with a Session. (subject)
- [MQTT-SN-3.6.2.2-1] Bits 3-2 of the PUBLISH Flags are reserved and MUST be set to 0. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.2.2-2] The receiver MUST validate that the reserved flags in the PUBLISH packet are set to 0. If any of the reserved flags is not 0 it is a Malformed Packet. (receiver of PUBLISH)
- [MQTT-SN-3.6.2.2.3-1] If the QoS field is set to 0 or 1, the DUP flag MUST be set to 0. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.2.3-1] If the QoS field is set to 0, the Packet Identifier field MUST not be present in the PUBLISH packet. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.2.3-2] If the QoS field is set to 1 or 2, the Packet Identifier field MUST be present in the PUBLISH packet. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.2.5-1] If the Topic Type is Topic Name (0b11), the Topic Name field MUST be present in the PUBLISH packet. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.2.5-2] If the Topic Type is Predefined Topic Alias or Session Topic Alias, then the Topic Name field MUST NOT be present in the PUBLISH packet. (sender of PUBLISH (packet format))
- [MQTT-SN-3.6.2.7-2] When Clients make subscriptions with Topic Filters that include wildcards, it is possible for a Client's subscriptions to overlap so that a published Application Message might match multiple filters. In this case the Server MUST deliver the Application Message to the Client respecting the maximum QoS of all the matching subscriptions. (subject)
- [MQTT-SN-3.7.6-1] When the Server receives a SUBSCRIBE packet from a Client, the Server MUST respond with a SUBACK packet. (subject)
- [MQTT-SN-3.8.2-1] Bits 7-3 of the SUBACK Flags are reserved and MUST be set to 0. (sender of SUBACK (packet format))
- [MQTT-SN-3.8.2.2-1] If the Topic Alias Flag is set to 0, a Topic Alias MUST NOT be present in the Packet. (sender of SUBACK (packet format))
- [MQTT-SN-3.8.2.2-2] If the Topic Alias Flag is set to 1, a Topic Alias MUST be present in the Packet. (sender of SUBACK (packet format))
- [MQTT-SN-3.8.4-2] If no Topic Alias is returned, the Topic Alias Flag MUST be 0. (sender of SUBACK (packet format))
- [MQTT-SN-3.8.4-3] If a Predefined Topic Alias was subscribed to, a Topic Alias MUST NOT be present in the SUBACK. (sender of SUBACK (packet format))
- [MQTT-SN-3.9.2-2] The Server MUST validate that the reserved flags in the UNSUBSCRIBE packet are set to 0. If any of the reserved flags is not 0 it is a Malformed Packet. (subject)
- [MQTT-SN-3.9.6-5] The Server MUST respond to an UNSUBSCRIBE request by sending an UNSUBACK packet. (subject)
- [MQTT-SN-3.9.6-6] The UNSUBACK packet MUST have the same Packet Identifier as the UNSUBSCRIBE packet. Even where no Topic Subscriptions are deleted, the Server MUST respond with an UNSUBACK. (subject)
- [MQTT-SN-3.11.3-1] The Server MUST send a PINGRESP packet in response to a PINGREQ packet after sending any buffered Application Messages, if it has a Virtual Connection for the sending Client. (subject)
- [MQTT-SN-3.11.3-2] The Server MAY send a DISCONNECT packet in response to a PINGREQ packet if it does not have a Virtual Connection for the sending Client. (subject)
- [MQTT-SN-3.11.3-4] If the state of the Client associated with the Virtual Connection is Asleep on receipt of the PINGREQ, the Server MUST move the Client to the Awake state, stop the Sleep Duration processing, and start the Retry Timer processing. (subject)
- [MQTT-SN-3.13.2-1] Bits 7-3 of the DISCONNECT Flags are reserved and MUST be set to 0. (sender of DISCONNECT (packet format))
- [MQTT-SN-3.13.2-2] The receiver MUST validate that the reserved flags in the DISCONNECT packet are set to 0. If any of the reserved flags is not 0 it is a Malformed Packet. (receiver of DISCONNECT)
- [MQTT-SN-3.13.2.1-1] If the Packet Identifier Flag is set to 0, a Packet Identifier MUST NOT be present in the Packet. (sender of DISCONNECT (packet format))
- [MQTT-SN-3.13.2.1-2] If the Packet Identifier Flag is set to 1, a Packet Identifier MUST be present in the Packet. (sender of DISCONNECT (packet format))
- [MQTT-SN-3.13.2.2-1] If the Session Expiry Interval Flag is set to 0, a Session Expiry Interval MUST NOT be present in the Packet. (sender of DISCONNECT (packet format))
- [MQTT-SN-3.13.2.2-2] If the Session Expiry Interval Flag is set to 1, a Session Expiry Interval MUST be present in the Packet. (sender of DISCONNECT (packet format))
- [MQTT-SN-3.13.2.3-1] If the Reason Code Flag is set to 0, a Reason Code MUST NOT be present in the Packet. (sender of DISCONNECT (packet format))
- [MQTT-SN-3.13.2.3-2] If the Reason Code Flag is set to 1, a Reason Code MUST be present in the Packet. (sender of DISCONNECT (packet format))
- [MQTT-SN-3.15.2-2] The Server MUST validate that the reserved flags in the SLEEPREQ packet are set to 0. If any of the reserved flags is not 0 it is a Malformed Packet. (subject)
- [MQTT-SN-3.15.5-2] If there is a Virtual Connection for the Client, the Server MUST send a SLEEPRESP packet in response to a SLEEPREQ packet. (subject)
- [MQTT-SN-3.15.5-3] If there is no Virtual Connection associated with the SLEEPREQ, the Server MAY send a DISCONNECT with Reason Code 0xF4 (No Virtual Connection Exists) in response. (subject)
- [MQTT-SN-3.15.5-4] If the SLEEPREQ request is granted, the Server MUST suspend Keep Alive processing for the Virtual Connection. (subject)
- [MQTT-SN-3.15.5-5] If the SLEEPREQ request is granted, the Server MUST start Sleep Duration processing for the Virtual Connection. (subject)
- [MQTT-SN-3.15.5-7] If the Client is already in the Asleep state when a SLEEPREQ is received by the Server, the Server MUST stop the Sleep Duration Timer, and start a new sleep cycle using the updated Sleep Duration. (subject)
- [MQTT-SN-3.16.2-1] Bits 7-1 of the SLEEPRESP Flags are reserved and MUST be set to 0. (sender of SLEEPRESP (packet format))
- [MQTT-SN-3.16.2.1-1] If the Sleep Duration Flag is set to 0, Sleep Duration MUST NOT be present in the Packet. (sender of SLEEPRESP (packet format))
- [MQTT-SN-3.16.2.1-2] If the Sleep Duration Flag is set to 1, Sleep Duration MUST be present in the Packet. (sender of SLEEPRESP (packet format))
- [MQTT-SN-3.16.2.1-3] If the Allow Server Suggested Values Flag in the CONNECT Packet that created the current Virtual Connection was 0, the Server MUST set the Sleep Duration Flag in the SLEEPRESP Packet to 0. (subject)
- [MQTT-SN-3.16.4-2] If the Server does not send the Sleep Duration, the Server MUST use the Sleep Duration value set by the Client in the SLEEPREQ packet. (subject)
- [MQTT-SN-3.17.2.1-1] The Monotonic Counter Length MUST NOT be set to 0x3 - the value is reserved. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.1-2] If the Monotonic Counter Length is set to 0x2, a Monotonic Counter of 32 bits (4 bytes) in length MUST be present in the Protection Encapsulation. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.1-3] If the Monotonic Counter Length is set to 0x1, a Monotonic Counter of 16 bits (2 bytes) in length MUST be present in the Protection Encapsulation. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.1-4] If the Monotonic Counter Length is set to 0x0, a Monotonic Counter MUST NOT be present in the Protection Encapsulation. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.2-1] If the Cryptographic Material Length is set to 0x3, a Cryptographic Material field of 96 bits (12 bytes) in length MUST be present in the Protection Encapsulation. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.2-2] If the Cryptographic Material Length is set to 0x2, a Cryptographic Material field of 32 bits (4 bytes) in length MUST be present in the Protection Encapsulation. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.2-3] If the Cryptographic Material Length is set to 0x1, a Cryptographic Material field of 16 bits (2 bytes) in length MUST be present in the Protection Encapsulation. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.2-4] If the Cryptographic Material Length is set to 0x0, a Cryptographic Material field MUST NOT be present in the Protection Encapsulation. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.3-1] If the Protection Scheme is not "Authentication Only" the Authentication Tag Length MUST be set to 0x1. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.2.3-3] The Authentication Tag Length MUST NOT be set to 0x2 or 0x3 - these values are reserved. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-3.17.3-1] The Protection Scheme is a one byte field which MUST contain one of the indexes in [tab](#tab-protection-schemes) which is not reserved. (sender of PROTECTION ENCAPSULATION (packet format))
- [MQTT-SN-4.1.1-1] The Server MUST NOT discard the Session State while the Virtual Connection exists. (subject)
- [MQTT-SN-4.1.1-3] The Server MUST discard the Session State when the Virtual Connection is deleted and the Session Expiry Interval has passed. (subject)
- [MQTT-SN-4.1.2-1] If the Client provides no client identifier, the Server MUST respond with a CONNACK containing an Assigned Client Identifier. (subject)
- [MQTT-SN-4.4.1-1] When a Client reconnects with Clean Start set to 0 and a Session is present, both the Client and Server MUST resend any unacknowledged PUBLISH with QoS 1 and 2 packets (not QoS 0) and PUBREL packets using their original Packet Identifiers. (subject)
- [MQTT-SN-4.4.2-3] A Server MUST respond promptly to a valid request Packet. (subject)
- [MQTT-SN-4.6-2] By default, a Server MUST treat every Topic as an Ordered Topic when it is forwarding Application Messages. (subject)
- [MQTT-SN-4.7.1.2-1] The Server MUST NOT match Topic Filters starting with a wildcard character (# or +) with Topic Names beginning with a \$ character. (subject)
- [MQTT-SN-4.7.1.3-4] When it performs subscription matching the Server MUST NOT perform any normalization of Topic Names or Topic Filters, or any modification or substitution of unrecognized characters. (subject)
- [MQTT-SN-4.7.2.2-5] If a Client requests a Session Topic Alias for a Topic Name which already has a Predefined Topic Alias, the Server MUST return a REGACK with the Topic Type "Predefined Topic Alias", the Predefined Topic Alias, and the Reason Code "Topic Alias Exists". (subject)
- [MQTT-SN-4.11.1-6] If the Client does not include an Authentication Method in the CONNECT, the Server MUST NOT send an AUTH packet, and it MUST NOT send an Authentication Method in the CONNACK packet. (subject)
- [MQTT-SN-4.11.1.1-2] If the re-authentication fails, the Client or Server MUST send DISCONNECT with an appropriate Reason Code as described in [sec](#handling-errors), and MUST delete the Virtual Connection. (subject)
- [MQTT-SN-4.12.1-2] When a Server detects a Malformed Packet or Protocol Error for any packet except ADVERTISE, SEARCHGW, GWINFO, PUBWOS and CONNECT, the Server MAY send a DISCONNECT packet with an appropriate Reason Code and MUST delete the associated Virtual Connection if one exists. (subject)
- [MQTT-SN-4.13-1] If the RETAIN flag is set to 1 in a PUBLISH or PUBWOS packet received by a Server, the Server MUST replace any existing Retained Message for this topic and store the Application Message. (subject)
- [MQTT-SN-4.13-4] If the RETAIN flag is 0 in a PUBLISH packet sent by a Client to a Server, the Server MUST NOT store the message as a Retained Message and MUST NOT remove or replace any existing Retained Message. (subject)
- [MQTT-SN-4.13-5] If Retain Handling is set to 0 the Server MUST send the retained messages matching the Topic Filter of the subscription to the Client. (subject)
- [MQTT-SN-4.13-6] If Retain Handling is set to 1 then if the subscription did not already exist, the Server MUST send all retained messages matching the Topic Filter of the subscription to the Client, and if the subscription did exist the Server MUST NOT send the retained messages. (subject)
- [MQTT-SN-4.13-7] If Retain Handling is set to 2, the Server MUST NOT send the retained messages. (subject)
- [MQTT-SN-4.13-8] If the value of Retain As Published subscription option is set to 0, the Server MUST set the RETAIN flag to 0 when forwarding an Application Message regardless of how the RETAIN flag was set in the received PUBLISH packet. (subject)
- [MQTT-SN-4.13-9] If the value of Retain As Published subscription option is set to 1, the Server MUST set the RETAIN flag equal to the RETAIN flag in the received PUBLISH packet. (subject)
- [MQTT-SN-4.14-1] A Server MUST treat any Packet other than PUBWOS or CONNECT that it receives from a Client in None or Disconnected states as a protocol error. (subject)
- [MQTT-SN-4.14.2-2] During the Asleep state, packets that need to be sent to the client are buffered at the Server. The Server MUST buffer Application Messages of QoS 1 and 2. (subject)
